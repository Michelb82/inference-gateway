# GW-17: Manifest-defined dynamic capabilities

## Problem

System prompts and input limits now come from the manifest, but capability IDs and behavior still depend on Go constants, Known(), and switches in request mapping, prompt construction, and result parsing. Adding or removing capabilities still requires rebuilding the gateway.

## Impact

- Manifests cannot define a new capability or enable only a subset.
- HTTP model listing, management discovery, and validation describe a compiled-in catalog.
- Making only Known() dynamic would still leave new capabilities unable to execute.

## Shorthand solution

Build the runtime registry entirely from capability_models. Describe input mapping, prompt variables, and optional JSON output validation in manifest entries, using generic gateway processing instead of capability-name switches. Separate public runtime operations in capability.go from registry construction in capability_registration.go and shared definition checks in capability_validation.go; keep holder synchronization in holder.go, within the same package. Avoid forwarding wrappers just to keep exported functions in one file. Keep mandatory explicit system_prompt and max_input_chars (200–500000), Redis scheduling, inference providers, and caller override policy.

## Status

Implemented: arbitrary manifest-defined IDs, input mapping, locale variables, declarative output validation, immutable registry snapshots, and consistent HTTP admission. Prompt variables declare explicit default/allowed values, support multiple language pairs per capability, and reject disallowed request selections before queueing and again during worker processing. Management support contract/manifest format are version 2. Custom capability lifecycle, queued removal, in-flight reload, and concurrency coverage are included. Detailed steps and acceptance criteria are in [the implementation plan](plan/gw-17-dynamic-capabilities.md).

## Local migration notes

The private local manifest was migrated from models to inference_endpoint, preserving its OpenAI-compatible provider and three configured capability IDs. The distribution sample now declares consistent per-capability limits on every rank and uses a provider.example placeholder for its inactive OpenAI endpoint. Both were checked with the production parser and resolver; the live debug guide documents validation and testing with the environment-provided key.
